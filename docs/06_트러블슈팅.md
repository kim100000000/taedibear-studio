**[004] 작업 환경 샌드박스에서 npm install 403 에러**
- 발생일: 2026-06-27
- 문제 상황: Claude의 작업 샌드박스에서 `npm install` 및 `npm view` 실행 시 패키지 종류와 무관하게 전부 `403 Forbidden (blocked-by-allowlist)` 에러 발생

- 참고 링크: -

**[005] AI 캡션 생성 API 호출 시 항상 429 에러 발생**
- 발생일: 2026-06-29
- 문제 상황: `POST /api/posts/caption` 호출 시 매번 `{"success":false,"error":"잠시 후 다시 시도해주세요."}` (429) 응답
- 원인: `.env`의 `GEMINI_MODEL`이 `gemini-2.0-flash`로 설정되어 있었는데, 해당 모델이 2026-06-01자로 deprecated 처리되어 더 이상 정상 호출이 안 됨 (에러 핸들링 로직이 이를 분당 요청 한도 초과(429)로 잘못 분류해서 표시)
- 해결 방법: `GEMINI_MODEL`을 무료 플랜에서 사용 가능한 최신 모델인 `gemini-2.5-flash`로 변경 (`.env`, `.env.example`, `gemini.service.js` fallback 값, `docs/05_API명세서.md` 모두 업데이트). 추가로 `posts.controller.js`에 에러 발생 시 실제 원인을 서버 콘솔에 로그로 남기도록 보강
- 참고 링크: https://ai.google.dev/gemini-api/docs/pricing

**[006] Meta(인스타그램) 연동 콜백 URL 불일치**
- 발생일: 2026-06-29
- 문제 상황: 인스타그램 연동(`/api/instagram/connect`) 후 Meta 로그인 화면에서 리다이렉트가 정상적으로 돌아오지 않음
- 원인: `.env`/`.env.example`의 `META_REDIRECT_URI`가 `http://localhost:4000/api/auth/meta/callback`으로 설정되어 있었지만, 실제 서버에는 `instagramRoutes`가 `/api/instagram`에 마운트되어 있어 콜백 경로가 `http://localhost:4000/api/instagram/callback`이어야 함
- 해결 방법: `.env`, `.env.example`의 `META_REDIRECT_URI`를 `http://localhost:4000/api/instagram/callback`으로 수정. Meta 개발자 콘솔(앱 설정 > 유효한 OAuth 리디렉션 URI)에도 동일한 값을 등록해야 함
- 참고 링크: -

**[007] 로그인 시 "Unknown column 'naver_id' in 'SELECT'" 에러**
- 발생일: 2026-06-29
- 문제 상황: `POST /api/auth/login` 호출 시 500 에러, 콘솔에 `Unknown column 'naver_id' in 'SELECT'`
- 원인: `User` 모델에 네이버 로그인용 `naverId` 컬럼을 추가했지만, 서버 시작 시 `sequelize.sync()`는 이미 존재하는 테이블에는 새 컬럼을 추가해주지 않음(테이블이 없을 때만 생성). 그래서 모델 코드에는 `naver_id`가 있지만 실제 DB의 `users` 테이블에는 해당 컬럼이 없는 상태로 어긋남
- 해결 방법: `backend/src/server.js`의 `sequelize.sync()`를 `sequelize.sync({ alter: true })`로 변경(개발 환경 한정). 서버를 재시작하면 모델 기준으로 누락된 컬럼이 기존 테이블에 자동으로 추가됨
- 참고 링크: -

**[008] 온보딩 보너스 크레딧 무한 반복 지급 가능**
- 발생일: 2026-07-02
- 문제 상황: `POST /api/users/me/onboarding-complete`를 API로 직접 반복 호출하면 호출할 때마다 크레딧 +2. 프론트는 localStorage 플래그로 모달을 한 번만 띄우지만 서버에는 아무 가드가 없었음
- 원인: "1회만"이라는 정책이 주석으로만 존재하고 서버 코드에 강제 장치가 없음. 프론트엔드 제한을 보안 장치로 착각한 사례
- 해결 방법: `users.onboarding_completed` 컬럼 추가 + 지급 전 플래그 검사(멱등 처리) + 행 잠금(`FOR UPDATE`)으로 동시 요청 차단. 상세: `09_크레딧버그수정_학습노트.md`
- 참고 링크: -

**[009] 크레딧 로직 전반의 race condition (동시 요청으로 제한 우회)**
- 발생일: 2026-07-02
- 문제 상황: 크레딧 차감·광고 충전 하루 2회 제한·무료 플랜 월 10회 제한이 모두 "읽고 → 검사 → 쓰기" 패턴이라, 같은 사용자의 동시 요청 2개가 모두 검사를 통과함 (크레딧 1개로 캡션 2회 등)
- 원인: `@Transactional`은 원자성만 보장할 뿐 동시 읽기를 막지 않음 (MySQL REPEATABLE READ의 일반 SELECT는 잠금 없는 스냅샷 읽기)
- 해결 방법: ① 단순 차감은 원자적 UPDATE (`update ... set credits = credits - 1 where credits > 0`, `@Modifying(clearAutomatically = true)`) ② 복합 검사(광고 2회 제한, 월 10회 제한)는 `@Lock(PESSIMISTIC_WRITE)` 행 잠금으로 직렬화. 잠금 메서드는 `@Transactional(propagation = MANDATORY)`로 트랜잭션 밖 호출을 차단
- 참고 링크: https://docs.spring.io/spring-data/jpa/reference/jpa/modifying-queries.html

**[010] 광고 시청 크레딧 충전이 실제 시청 여부를 검증하지 않음**
- 발생일: 2026-07-02

- 참고 링크: https://support.google.com/admob/answer/9603226

**[011] bootRun 시 WeakKeyException — .env가 로드되지 않아 JWT 기본 secret 사용됨**
- 발생일: 2026-07-03
- 문제 상황: 터미널에서 `./gradlew bootRun` 실행 시 `WeakKeyException: The specified key byte array is 144 bits...`로 부팅 실패
- 원인: Spring Boot는 Node(dotenv)와 달리 `.env` 파일을 자동으로 읽지 않음. 환경변수 없이 실행하면 `application.yml`의 기본값 `change_this_secret`(18바이트=144비트)이 사용되고, jjwt가 HS256 최소 256비트 요건 미달로 예외를 던짐 (보안 보고서 C8이 실제로 확인된 사례)
- 해결 방법: 실행 전 `.env`를 셸에 로드 — `set -a; source .env; set +a` 후 `./gradlew bootRun`. JWT_SECRET은 `openssl rand -base64 48`로 32바이트 이상 값 사용
- 참고 링크: https://github.com/jwtk/jjwt#signing-key

**[012] APPLICATION FAILED TO START — WebClient 빈 없음 (PaymentService)**
- 발생일: 2026-07-03

- 해결 방법: `WebClientConfig`에 `WebClient` 빈 추가 (`builder.build()`)

**[013] MariaDB + ddl-auto:update 조합의 DDL 경고 다수 (무시 가능)**
- 발생일: 2026-07-03
- 문제 상황: 부팅 시 `Cannot change column 'id': used in a foreign key constraint` WARN 다수 + `Unknown column 'RESERVED' in 'WHERE'` 경고
- 원인: Hibernate의 `update` 모드가 기존 FK 컬럼 정의를 다시 맞추려고 ALTER를 시도하지만 FK 제약 때문에 거부됨. 스키마 자체는 이미 올바르므로 실행에는 영향 없음. RESERVED 경고는 MySQL Connector/J가 MariaDB 12 메타데이터를 조회할 때의 호환성 문제
- 해결 방법: 당장은 무시 가능. 근본 해결은 `ddl-auto: validate` + Flyway 마이그레이션 전환 (보안 보고서 M7). MariaDB를 계속 쓸 거면 드라이버/dialect를 MariaDB용으로 맞추는 것도 검토
- 참고 링크: -
