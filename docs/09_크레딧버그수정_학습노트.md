## 버그 1. 온보딩 보너스 무한 반복 (H2)

### 무엇이 이상했나

주석에는 "1회만"이라고 적혀 있지만, 실제로 1회를 보장하는 코드가 없었다.
프론트엔드가 `localStorage`의 `onboarding_seen_${user.id}` 플래그로 모달을 한 번만 띄우기 때문에
**정상 사용자에게는 1회처럼 보이지만**, API를 직접 호출하면(curl, Postman) 무한 반복이 가능했다.

> 교훈: **프론트엔드의 제한은 UX일 뿐, 보안이 아니다.** 제한은 반드시 서버에서 강제해야 한다.

### 수정 전

```java
// Phase 2-1: 온보딩 완료 보너스 +2 크레딧 (1회만)   ← 주석뿐, 가드 없음
@Transactional
public int completeOnboarding(Long id) {
    User user = getById(id);
    user.setCredits(user.getCredits() + 2);   // 호출할 때마다 +2
    return user.getCredits();
}
```

### 수정 후

```java
// User 엔티티에 플래그 컬럼 추가
@Column(name = "onboarding_completed", nullable = false)
@Builder.Default
private boolean onboardingCompleted = false;
```

```java
@Transactional
public int completeOnboarding(Long id) {
    User user = getByIdForUpdate(id);          // 행 잠금 (버그 2 참고)
    if (user.isOnboardingCompleted()) {
        return user.getCredits();              // 이미 받았으면 그냥 현재 값 반환 (멱등)
    }
    user.setOnboardingCompleted(true);
    user.setCredits(user.getCredits() + 2);
    return user.getCredits();
}
```

### 설계 판단

- 이미 받은 경우 400 에러 대신 **현재 크레딧을 그대로 반환(멱등 처리)** 했다.
  프론트(`DashboardPage`)는 응답의 credits만 쓰므로 수정이 필요 없고,
  네트워크 재시도 등으로 중복 호출돼도 사용자에게 에러가 보이지 않는다.
- 플래그 검사만으로는 부족하다 — 동시에 2개의 요청이 들어오면 둘 다 `false`를 읽고
  둘 다 +2를 할 수 있다. 그래서 행 잠금(`getByIdForUpdate`)과 함께 사용한다.

## 버그 2. 크레딧 race condition (H1)

### 무엇이 이상했나

크레딧 로직 3곳이 전부 **"읽고 → 검사하고 → 쓰는(read-check-write)"** 패턴이었다.
이 패턴은 단일 요청에서는 문제가 없지만, 같은 사용자의 요청 2개가 **동시에** 들어오면 깨진다.

```
시간 →
요청 A: credits 조회(1) → 1 > 0 통과 → credits = 0 저장
요청 B:      credits 조회(1) → 1 > 0 통과 → credits = 0 저장   ← 끼어듦
결과: 크레딧 1개로 캡션 2회 생성됨
```

`@Transactional`이 있어도 막지 못한다 — 트랜잭션은 원자성(전부 성공/전부 실패)을 보장할 뿐,
**두 트랜잭션이 같은 행을 동시에 읽는 것 자체는 막지 않기 때문이다** (MySQL 기본 격리수준 REPEATABLE READ의 일반 SELECT는 잠금을 걸지 않는 스냅샷 읽기).

같은 문제가 있던 곳: `deductCreditForCaption`(크레딧 차감), `watchAd`(하루 2회 제한), `PaymentService.checkPlanLimit`(무료 월 10회 제한).

### 해결 전략 — 두 가지 방법을 상황에 맞게

**방법 A: 원자적 UPDATE (조건을 UPDATE 문에 포함)**

검사와 변경을 SQL 한 문장으로 합치면 DB가 원자적으로 처리한다. 가장 가볍고 빠르다.
단순한 "조건부 증감"에 적합.

**방법 B: 비관적 잠금 (SELECT ... FOR UPDATE)**

행을 읽는 시점에 쓰기 잠금을 걸어, 다른 트랜잭션이 커밋될 때까지 대기하게 한다.
"여러 필드를 읽고 복잡한 검사 후 여러 필드를 쓰는" 로직에 적합.

### 수정 전 / 후 ① — 크레딧 차감 (방법 A)

```java
// 수정 전 — 읽고 검사하고 쓰기 (끼어들기 가능)
@Transactional
public void deductCreditForCaption(Long id) {
    User user = getById(id);
    if (user.getPlan() == Plan.pro) return;
    if (user.getCredits() <= 0) {
        throw ApiException.forbidden("크레딧이 부족해요. 광고를 보고 충전해주세요.");
    }
    user.setCredits(user.getCredits() - 1);
}
```

```java
// 수정 후 — UserRepository에 원자적 차감 쿼리 추가
@Modifying(clearAutomatically = true)
@Query("update User u set u.credits = u.credits - 1 where u.id = :id and u.credits > 0")
int deductOneCredit(@Param("id") Long id);
```

```java
// 서비스: 반환값(영향받은 행 수)으로 성공/실패 판정
@Transactional
public void deductCreditForCaption(Long id) {
    User user = getById(id);
    if (user.getPlan() == Plan.pro) return;

    int updated = userRepository.deductOneCredit(id);
    if (updated == 0) {   // credits > 0 조건 불충족 → 차감 안 됨
        throw ApiException.forbidden("크레딧이 부족해요. 광고를 보고 충전해주세요.");
    }
}
```

`credits > 0` 검사가 UPDATE 문 안에 있어서, 동시에 100개 요청이 와도 크레딧 수만큼만 성공한다. 음수가 될 수 없다.

### 수정 전 / 후 ② — 광고 시청 / 온보딩 / 월 제한 (방법 B)

`watchAd`는 날짜 비교 + 카운트 검사 + 3개 필드 갱신이라 UPDATE 한 문장으로 만들기 복잡하다.
이런 경우 행 잠금이 깔끔하다.

```java
// UserRepository에 잠금 조회 추가
@Lock(LockModeType.PESSIMISTIC_WRITE)          // → SELECT ... FOR UPDATE
@Query("select u from User u where u.id = :id")
Optional<User> findByIdForUpdate(@Param("id") Long id);
```

```java
// 수정 전
User user = getById(id);              // 일반 SELECT — 동시 읽기 허용
// 수정 후
User user = getByIdForUpdate(id);     // FOR UPDATE — 두 번째 요청은 첫 번째가 끝날 때까지 대기
```

`PaymentService.checkPlanLimit`(무료 월 10회)도 같은 문제가 있었다:
"이번 달 게시물 카운트 조회 → 10 미만 검사 → INSERT" 사이에 다른 요청이 끼어들면 10회를 초과할 수 있다.
게시물 수는 users 행이 아니라 posts 테이블이라 원자적 UPDATE로 못 풀고,
**사용자 행을 잠금으로 삼아 요청을 직렬화**하는 방식을 썼다:

```java
@Transactional(propagation = Propagation.MANDATORY)  // 반드시 호출자 트랜잭션 안에서 실행
public void checkPlanLimit(Long userId) {
    User user = userRepository.findByIdForUpdate(userId)   // ← 여기서 직렬화
            .orElseThrow(() -> ApiException.notFound("사용자를 찾을 수 없어요."));
    if (user.getPlan() == Plan.pro) return;
    // ... 카운트 조회 → 검사 (잠금 덕분에 이 사이에 끼어들 수 없음)
}
```

`Propagation.MANDATORY`를 붙인 이유: 비관적 잠금은 **트랜잭션이 없으면 의미가 없다**
(잠금이 즉시 풀려버림). 실수로 트랜잭션 밖에서 호출하면 조용히 뚫리는 대신 예외가 나게 강제했다.

## 버그 3. 광고 시청 미검증 (H3) — 부분 수정

### 무엇이 이상했나

`POST /api/users/me/credits/ad-watch`는 **광고를 실제로 봤는지 전혀 확인하지 않는다.**
클라이언트가 그냥 POST만 보내면 +1 크레딧. 스크립트로 연타하면 (하루 2회 제한의 race와 결합해) 그 이상도 가능했다.

### 이번에 고친 것

1. 행 잠금으로 하루 2회 제한의 race condition 제거 (버그 2와 동일 방식)
2. **최소 시청 간격 30초** 추가 — 리워드 광고는 보통 15~30초 재생되므로,
   30초 안에 두 번째 충전 요청이 오면 물리적으로 광고를 봤을 수 없다.

```java
// User 엔티티에 마지막 충전 시각 컬럼 추가
@Column(name = "last_ad_watch_at")
private LocalDateTime lastAdWatchAt;
```

```java
// watchAd 앞부분에 간격 검사 추가
if (user.getLastAdWatchAt() != null
        && Duration.between(user.getLastAdWatchAt(), now).getSeconds() < MIN_AD_INTERVAL_SECONDS) {
    throw ApiException.badRequest("광고 시청 후 잠시 뒤에 다시 시도해주세요.");
}
```

### 고치지 못한 것 (한계 명시)

"실제로 광고를 봤는가"는 서버 혼자서는 알 수 없다.
근본 해결은 광고 네트워크의 **SSV(Server-Side Verification)** — 광고 SDK가 시청 완료 시
광고사 서버가 우리 서버로 서명된 콜백을 보내고, 그 콜백에서만 크레딧을 지급하는 방식이다.
광고 SDK를 붙이는 시점에 이 엔드포인트를 SSV 콜백 방식으로 교체해야 한다. (코드에 TODO 주석 남김)

## 트러블슈팅

**[T-1] 샌드박스에서 빌드 검증 불가**

- 문제 상황: 수정 후 `./gradlew compileJava` 실행 시도 → 샌드박스에 Java 11만 설치되어 있고(프로젝트는 17 필요), Maven Central·Adoptium JDK 다운로드가 네트워크 allowlist에 막힘(`403 blocked-by-allowlist`)
- 시도한 방법: ① gradle 백그라운드 실행 → 세션 간 프로세스 유지 안 됨 ② apt로 JDK 17 설치 → root 권한 없음 ③ JDK tarball 직접 다운로드 → allowlist 차단
- 결론: 샌드박스 빌드 불가. 대신 수정 파일 4개의 참조 일관성(새 필드/메서드명, import, 호출부)을 grep으로 전수 검증함. **로컬에서 `./gradlew compileJava` 실행 필요.**

**[T-2] `@Modifying` 쿼리와 영속성 컨텍스트 불일치 주의**

- 문제 상황(예방): JPQL bulk UPDATE는 DB에 직접 실행되므로, 이미 조회해 둔 엔티티(1차 캐시)의 credits 값은 갱신 전 값으로 남는다. 이후 그 엔티티를 저장하면 차감이 되돌려질 수 있다
- 해결 방법: `@Modifying(clearAutomatically = true)`로 쿼리 실행 후 영속성 컨텍스트를 비워 stale 엔티티 사용을 방지. `deductCreditForCaption`은 차감 후 엔티티를 다시 쓰지 않으므로 안전
- 참고: https://docs.spring.io/spring-data/jpa/reference/jpa/modifying-queries.html

**[T-3] 비관적 잠금은 트랜잭션 밖에서 조용히 무력화됨**

- 문제 상황(예방): `PESSIMISTIC_WRITE`는 트랜잭션 커밋/롤백 시점에 잠금이 풀린다. 트랜잭션 없이 호출하면 에러 없이 잠금만 사라져 race condition이 재발한다
- 해결 방법: `checkPlanLimit`에 `@Transactional(propagation = Propagation.MANDATORY)` — 호출자 트랜잭션이 없으면 `IllegalTransactionStateException`이 나도록 강제. "조용히 뚫리는 것"보다 "시끄럽게 실패하는 것"이 낫다

**[T-4] 새 컬럼 2개 — 개발 DB는 자동 반영, 운영은 주의**

- 문제 상황: `users` 테이블에 `onboarding_completed`, `last_ad_watch_at` 컬럼 추가됨
- 해결 방법: 개발 환경은 `ddl-auto: update`라 서버 재시작 시 자동 추가됨. 단 `onboarding_completed`는 `nullable = false`인데, **기존 사용자 행에는 기본값 없이 컬럼이 추가되면 실패할 수 있음** → 재시작 후 에러 시 `ALTER TABLE users ADD COLUMN onboarding_completed TINYINT(1) NOT NULL DEFAULT 0;` 수동 실행. 운영 전환 시에는 Flyway 마이그레이션으로 관리할 것 (보고서 M7)
- 참고: 기존 사용자는 전부 `onboarding_completed = false`가 되므로, 이미 보너스를 받은 사용자가 한 번 더 받을 수 있다. 사용자가 적은 지금은 무시 가능한 수준이지만, 마이그레이션 시 `credits >= 5`인 사용자를 true로 세팅하는 식의 보정도 고려할 수 있음
